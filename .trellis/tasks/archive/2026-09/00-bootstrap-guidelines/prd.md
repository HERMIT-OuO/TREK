# TREK 项目开发规范初始化

## 目标

将 `.trellis/spec/` 的初始化模板整理为基于 TREK 当前源码、测试和现有约定的中文开发规范，使后续开发者与 AI 能准确找到代码入口、遵循真实契约，并选择正确的验证方式。

## 背景与已确认事实

- 用户已授权复用 `.trellis/tasks/00-bootstrap-guidelines/`，并在最终规划摘要后明确回复“可以，开始吧”；任务已通过 `task.py start` 激活，不另建重复任务。
- 初始规范为脚手架：client/frontend、server/backend、server/frontend、shared/backend、shared/frontend，均含待填写内容；guides 为通用思考指南。
- npm 工作区为 client、server、shared；plugin-sdk 是仓库内独立安装、独立发布的 SDK/CLI，不属于 npm 根工作区。
- 现有根目录及各包的 `CLAUDE.md`、页面模式文档和测试可作规范来源，但存在与当前实现不一致的历史说明，不能照搬。

## 需求与范围

### R1：按真实职责组织规范

覆盖客户端、服务端、共享契约库、插件 SDK，以及跨包开发指南。纠正不适用的模板分类，使共享契约不再重复套用前端组件或数据库规范。服务端提供 HTML/插件页面的边界能力仍需说明，但不据此虚构一个 React 前端层。

### R2：提供可追溯的编码指导

每项重要规则应说明适用范围、推荐模式、真实源码或测试证据、常见错误及适用的验证方法。明确区分当前行为、现有文档规定的新代码约束、历史债务；不能将孤立实现推导为全项目规范。

### R3：覆盖高风险契约

至少覆盖页面与业务 Hook 分工、桌面/移动端共用逻辑、离线缓存与写入队列、实时事件、主题；Nest 模块与鉴权、Zod 校验、SQLite 事务与迁移、配置与日志；共享 Schema、i18n、构建导出；MCP 与 REST 一致性、插件隔离及宿主/SDK 协议一致性。

### R4：保留可靠的开发与验证入口

提供基于当前脚本的安装、运行和调试说明，区分只读检查与会改文件的命令、全量与定向验证。不得固化本机绝对路径、当前 Node 安装状态或某个 AI 平台为项目通用要求。

### R5：保持规范可发现、可维护

索引与最终文件集合一致，包含开发前检查项及质量检查入口。必要时最小调整 Trellis 包映射，让新增/重组后的规范被现有上下文发现机制识别；不得因此改动 npm 工作区成员。

## 非目标与限制

- 不修改产品源码、测试实现、依赖、CI、Docker 或部署配置，不顺带修复技术债务。
- 不修改现有 `CLAUDE.md`、平台技能、代理配置或 Trellis 运行时脚本。
- 不安装外部索引服务，不上传代码；分析工具不可用时使用本地源码与测试。
- 不执行发布、账号初始化、数据库重置，不自动 commit、push、archive。
- 保留当前工作区已有改动。现有 spec 中若发现实际用户内容，必须先保留并整合，而非按模板直接删除。

## 验收标准

- AC1（R1、R5）：规范包/层与实际职责一致，包发现输出可列出 client、server、shared、plugin-sdk 的有效规范入口；没有与实际职责不符的空模板层。
- AC2（R2、R3）：重要规则可追溯到存在的源码、测试或有效约定；高风险领域具有实际代码/测试示例，不把迁移历史当成当前架构。
- AC3（R2、R5）：规范无待填写标记、空标题、示例模板残留、失效相对链接；所有主题均可从索引找到。
- AC4（R4）：命令与 package.json/配置相符，明确 shared 构建顺序、插件 SDK 独立性、后端 build 与 typecheck 的区别及 TypeScript 断点前提。
- AC5（R5）：已有任务上下文引用不因目录调整失效；`get_context.py --mode packages` 和任务 JSONL 校验通过。
- AC6（所有需求）：最终变更限于规范、必要的 Trellis 包映射、当前任务产物；业务文件保持不变，检查结果和未执行项如实记录。

## 审批边界

用户已明确批准本 PRD、design.md、implement.md 和最终规划摘要，现已进入执行阶段。该批准仅覆盖本文范围；涉及产品代码、依赖、平台集成或发布行为的扩大变更必须重新确认。
